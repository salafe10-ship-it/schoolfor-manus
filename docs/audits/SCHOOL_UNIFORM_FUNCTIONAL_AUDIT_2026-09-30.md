# تدقيق وحدة الزي المدرسي — قرار الانتقال إلى المخزون

**التاريخ:** 2026-09-30  
**النطاق:** الشاشات، الأزرار، المصدر المركزي، المخزون، والحسابات العامة.

## القرار

وحدة الزي **مراجعة ومحصورة في وضع التشغيل الآمن**. الربط المركزي القابل للإثبات موجود في تعريف الأصناف والمتغيرات والبيع، لكن الوحدة ليست مكتملة لكل دورة الشراء والاستلام والتوريد. لذلك لا نعلن إغلاقها كدورة تجارية كاملة، وننتقل إلى وحدة المخزون لمعالجة نقطة المصدر المشتركة.

## ما تم إثباته

| المسار | النتيجة |
|---|---|
| قراءة أصناف الزي | عبر `/api/uniform/items` وبنطاق المدرسة |
| قراءة المتغيرات والأرصدة | عبر `/api/uniform/variants` وبنطاق المدرسة |
| إنشاء صنف | حفظ مركزي مع تدقيق وإنشاء متغير افتراضي |
| إنشاء متغير | حفظ مركزي مع حركة افتتاحية عند وجود رصيد |
| حركة المخزون | معاملة مركزية، قفل صف، منع الرصيد السالب، وقيد GL |
| بيع الزي | معاملة واحدة تخصم المخزون وتسجل حركة البيع وتكلفة البضاعة وقيد GL |
| الحماية من البيانات الوهمية | ناجحة؛ لا تظهر بذور محلية في الوضع الكانوني |
| الاختبارات المرتبطة | 8 ملفات، 10 اختبارات ناجحة |

## مراجعة الشاشات والأزرار

### تعمل أو تتوقف بأمان

- لوحة المؤشرات تعرض أرقامًا صفرية/غير متاحة عند غياب مصدر مركزي بدل اختلاق مبيعات.
- شاشة الأصناف تقرأ من المصدر المركزي، وإنشاء الصنف يرفض البيانات غير الصالحة.
- شاشة الأرصدة تعرض المتغيرات المركزية فقط.
- سلة البيع تمنع البيع عند نقص الرصيد، ومسار البيع المركزي ينشئ القيد المحاسبي.
- الأزرار التي لا تملك مسارًا مركزيًا لا تعرض نجاحًا وهميًا؛ بعضها يعرض رسالة توقف واضحة.

### فجوات مؤكدة

1. **استلام أمر الشراء:** الزر متوقف عمدًا لأن أمر الشراء وبنوده لا يملكان مستودعًا مركزيًا كاملًا داخل وحدة الزي؛ الكود القديم بعد `return` غير قابل للتنفيذ ولا يُعتبر مسارًا صالحًا.
2. **الموردون:** الإضافة محلية/محاكاة SQL في الواجهة عند الوضع الكانوني، وليست مرتبطة بمسار مورد مركزي.
3. **تعديل الأسعار الجماعي:** متوقف في الوضع الكانوني لغياب endpoint مركزي.
4. **قياسات الطلاب والحجوزات والمرتجعات:** لا يوجد مسار مركزي كامل مثبت لكل دورة العمل.
5. **المبيعات:** المسار موجود ومربوط بالمخزون وGL، لكنه يحتاج UAT مصرحًا ببيانات طالب وصنف فعليين قبل اعتماد دورة البيع التجارية.

## الربط المحاسبي والمخزني

المسار الصحيح المثبت حاليًا:

`uniform_item_variants` → `uniform_stock_movements` → `erp_journal_entries` / `erp_general_ledger`

في الشراء/الزيادة يستخدم الأصل المخزني `1301` مقابل الالتزام `2101`. وفي البيع يستخدم الأصل النقدي/حساب الطالب مقابل الإيراد `4101` وتكلفة البضاعة `5270` وخفض المخزون `1301`. كل ذلك داخل معاملة واحدة مع سجل تدقيق.

لا يجوز اعتماد حسابات الواجهة القديمة مثل `1205_UNIFORM_STOCK` أو `4105_UNIFORM_REV`؛ فهي جزء من المسار المحلي القديم المتوقف وليست دليلًا على ترحيل كانوني.

## ما ينتقل إلى وحدة المخزون

1. توحيد بطاقة الصنف والمتغيرات والمقاسات والألوان.
2. توحيد المورد وأمر الشراء والاستلام والفاتورة.
3. جعل حركة الاستلام المخزني المصدر الوحيد لزيادة الرصيد.
4. ربط الاستلام والبيع والمرتجع بقيود GL كانونية قابلة للتتبع.
5. توفير idempotency، عكس حركة معتمد، وتسوية رصيد مع سجل التدقيق.

## قرار الانتقال

**تم إنهاء تدقيق وحدة الزي المدرسي دون إعلان اكتمال تجاري زائف.** الوحدة صالحة للقراءة وإنشاء الأصناف والبيع المركزي بعد UAT، أما دورة الشراء والاستلام والموردين فتنتقل إلى وحدة المخزون باعتبارها مالك المخزون والمصدر المشترك للحسابات العامة.

## تحديث جسر الترحيل — 2026-09-30

أُغلق الانحراف المحاسبي الذي كان يسمح لمسارات الزي باستدعاء `syncSnapshot` العام مباشرة. أصبحت عمليات الرصيد الافتتاحي، حركة المخزون، ومبيعات الزي تمر عبر `syncInventoryProcurementSnapshot`، مع مستندات مخزنية قابلة للتتبع ومصدر موحد للربط بالحسابات العامة. أضيف اختبار عقدي يمنع عودة المسار المباشر.

يبقى الفصل التشغيلي مقصودًا: جداول الزي تحفظ تفاصيل المقاس/اللون والبيع، بينما وحدة المخزون تظل مالك دورة التوريد العامة. لذلك لا تزال دورة المورد/أمر الشراء/الاستلام تُنفذ من المخزون، ولا يُعلن إغلاق هذه الدورة من شاشة الزي قبل استكمال UAT المرئي في بيئة المدرسة.
