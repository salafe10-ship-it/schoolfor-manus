# وحدة رسوم الطلاب — مسار العمليات الكانوني

## قاعدة التشغيل

الـ Snapshot القديم أصبح نموذج قراءة/توافق فقط. العمليات الجديدة تكتب إلى PostgreSQL في جداول موحدة داخل معاملة واحدة، مع عزل المدرسة، مفتاح تكرار، وسجل تدقيق.

## المسارات

| المسار | الغرض |
|---|---|
| `GET /api/financial/fee-templates` | قراءة قوالب الرسوم من المصدر المركزي |
| `POST /api/financial/fee-templates` | إنشاء قالب رسم بإصدار وسنة وفترة وحساب إيراد |
| `POST /api/financial/fee-assignments/bulk` | توزيع رسم جماعي آمن من التكرار، مع خيار إصدار المطالبات |
| `POST /api/financial/invoices/issue` | إصدار مطالبة واحدة بمفتاح idempotency |
| `POST /api/financial/invoices/issue-batch` | إصدار عدة مطالبات في معاملة واحدة (إما كلها أو لا شيء) |
| `POST /api/financial/invoices/:invoiceId/void` | إلغاء المطالبة وعكس قيدها وخطتها في معاملة واحدة بعد التحقق من عدم وجود سداد فعّال |
| `POST /api/financial/invoices/:invoiceId/installment-plan` | إنشاء خطة أقساط محفوظة مع معالجة كسور المبالغ |
| `POST /api/financial/concessions` | طلب منحة/إعفاء يحتاج اعتمادًا |
| `POST /api/financial/concessions/:id/approve` | اعتماد المنحة أو الإعفاء وتسجيل القرار |
| `GET /api/financial/students/:studentId/account` | كشف حساب الطالب من الفواتير والدفعات المركزية |
| `POST /api/financial/payment-intents` | إنشاء محاولة دفع مرتبطة بمزود خارجي |
| `POST /api/financial/payment-webhooks/:provider` | استقبال Webhook موقّع وبشكل idempotent |
| `POST /api/financial/payment-attempts/:id/settle` | تحويل محاولة دفع ناجحة إلى سند قبض موثق |
| `POST /api/financial/receipts/:receiptId/allocate` | تخصيص السند على فاتورة وقسط محدد |
| `POST /api/financial/receipts/:receiptId/reverse` | عكس القيد والتخصيصات وأرصدة الفواتير والأقساط في معاملة واحدة |

## الضوابط

- لا توجد كتابة مالية جديدة إلى `FallbackStorage` أو ملفات JSON في staging/production.
- لا يمكن إعادة توزيع نفس الرسم للطالب في نفس السنة والفترة والقالب.
- لا يمكن أن تتجاوز الدفعة رصيد السند أو الفاتورة.
- لا يمكن تخصيص سند طالب على فاتورة طالب آخر أو قسط لا يتبع الفاتورة نفسها.
- مفاتيح إعادة المحاولة لا تعيد استخدام حركة ببيانات مختلفة؛ التوزيع الجماعي يعيد معرفات السجلات الأصلية عند التكرار.
- عكس السند يعلّم التخصيصات كمعكوسة ولا يحذف سجلها، ويعيد أرصدة الفواتير والأقساط مع القيد العكسي.
- السنة والفترة والحساب الإيرادي تُتحقق من المصدر الموثوق في الخادم ولا تُقبل من الواجهة وحدها.
- اعتماد المنحة معطّل مؤقتًا؛ لا يُسمح بعرض طلب على أنه معتمد قبل وجود أثر خصم وقيد محاسبي موثق.
- لا يمنح السلوك أو اسم ولي الأمر خصمًا تلقائيًا؛ يجب وجود سياق أسري ومنحة معتمدة.
- Webhook يحدّث حالة محاولة الدفع فقط؛ إنشاء السند والترحيل يتطلبان مستخدمًا ماليًا موثقًا.
- جميع عمليات الإنشاء والتعديل مرتبطة بـ `tenant_id` و`school_id`.

## متطلبات النشر

1. تطبيق migration `202609081500_canonical_student_fee_operations.sql`.
2. ضبط `EDUPRO_ENVIRONMENT=staging|production`.
3. ضبط `PAYMENT_WEBHOOK_SECRET` قبل استقبال Webhooks.
4. تشغيل اختبارات RLS على الجداول الجديدة.
5. عدم تفعيل بوابة الدفع قبل اختبار التسوية والتخصيص ورد المبالغ في بيئة staging.

## اختبار UAT لوحدة الرسوم على staging

تتطلب الاختبارات تطبيق migration `202610131000_student_fee_receipt_reversal_audit.sql`، ومستخدمًا ماليًا واثنين من طلاب الاختبار المخصصين بلا ذمم مفتوحة، وقالبًا نشطًا وبند رسوم متطابقين، وحساب إيراد وحساب قبض نقدي/مصرفي صالحين. السكربت يتحقق من هدف قاعدة البيانات ودورها قبل أي اتصال، ويستخدم واجهات التطبيق لكل الكتابات؛ وتبقى آثار الإلغاء والعكس في سجل التدقيق.

نجاح Vitest أو فحص GitHub Actions لا يعني نجاح UAT المالي. سير عمل `Production validation` يشغّل اختبارات المشروع والبناء فقط، وسير عمل `Staging uptime` يفحص `/api/health` فقط؛ لا ينشئان فواتير أو سندات ولا يتحققان من قاعدة staging.

انسخ `docs/student-fees-staging-uat.env.example` إلى `.env.staging` محليًا؛ `.env.staging` مستثنى من Git ويُقرأ مباشرة بواسطة السكربت، بينما `.env` العام لا يُستخدم. لا تنسخ قيم `.env` العامة إلى staging ولا تستخدم هدفًا قبل إثبات عزله. املأ `SUPABASE_URL` و`DATABASE_URL` من المصدر المعتمد بعد إثبات أن القاعدة staging وأن الدور `edupro_staging_app`، ثم أضف رمز UAT وبيانات الطلاب والقالب والحسابات المخصصة. اترك `UAT_STUDENT_FEES_STAGING_CONFIRM` فارغًا حتى يصبح التنفيذ جاهزًا، ثم اضبطه إلى `RUN_STUDENT_FEES_STAGING_UAT` صراحةً. لا تضع الأسرار في ملفات متتبعة أو مخرجات الاختبار.

شغّل `pnpm uat:student-fees:staging`. يختبر السكربت إصدار عدة بنود وإعادة الطلب، ذرّية الإصدار عند تعارض قاعدة البيانات، التوزيع مرتين متتاليتين بنفس المعرفات، خطة أقساط، قبضًا جزئيًا وكاملًا، رفض العزل بين طالبين، عكس السندات والتخصيصات والأقساط، ثم إلغاء المطالبات والتحقق من كشف الحساب. عند إخفاق خطوة، يحاول تنظيف السندات والمطالبات التي أنشأها، ويتحقق من حفظ العكس والإلغاء ويبلّغ عن أي أثر لم يستطع تنظيفه. لا تعتبر UAT ناجحًا إلا إذا انتهى الأمر بـ `success: true` وظهر التنظيف بلا أخطاء.
