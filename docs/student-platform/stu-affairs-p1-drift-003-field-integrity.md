# STU-AFFAIRS-P1-DRIFT-003 — Student Registration Field Integrity

## Scope

This review covers the registration path only:

`StudentAffairsPortal → StudentRepository → POST /api/students → server.ts → StudentRegistrationService → StudentRegistrationRepositories`

No schema, migration, RLS, Enrollment, Lifecycle, Guardian redesign, or UI feature was added.

## Findings and bounded implementation

- `nationality` and `birthCountryCode` already have an approved canonical Student command and persistence path.
- `admissionReference` is generated by the trusted server registration path and is persisted on the Enrollment record; it is not accepted from the browser.
- `classroom` and `section` belong to Enrollment placement, not `students`, as established by P1-006-18. No mapping was added.
- `status` belongs to the Academic Status/Lifecycle domain. Registration continues to use the canonical registration status and does not bind the browser value.
- `stage` has no proven canonical source. No mapping was invented.
- `address`, `email`, and `phone` have no approved Student persistence field in the current canonical schema. They remain unpersisted rather than being written to an unrelated column.
- Guardian name and phone are mapped from explicit `parentName` and `parentPhone` fields.
- Guardian email is now mapped only from explicit `parentEmail`. The prior fallback from the student's `email` was removed; student email can no longer be silently stored as guardian email.

## Decision

`P1-DRIFT-003 = PARTIAL / DOMAIN OR SCHEMA DEPENDENCY`

The unsafe synthetic guardian-email mapping is closed at code level. Remaining field gaps require approved Enrollment, Academic Status, or schema/domain decisions and are intentionally not implemented in this mission.
